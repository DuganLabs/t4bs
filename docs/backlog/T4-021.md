## What the user hits

A moderator working the queue on a phone taps once and the submission is gone. REJECT sits directly beside APPROVE as an equal half of the same row, 10px apart, with the destructive one on the right where the thumb rests — and it commits instantly, with no "are you sure", no undo, and no toast the moderator can act on. Once it is rejected there is no screen anywhere in Tabs that shows it again, so a mis-tap cannot be discovered, let alone reversed; the person who submitted the phrase is never told either way.

## Why it happens

Three separate things line up.

**No interstitial.** `src/views/moderate.js:61-65` delegates the click straight into the commit:

```js
queueRoot.addEventListener("click", (e) => {
  const btn = e.target.closest('button[data-action="mod-decide"]');
  if (!btn) return;
  decide(Number(btn.dataset.id), btn.dataset.decision);
});
```

and `decide()` (`src/views/moderate.js:24-33`) calls `api.modDecide(id, status)` on its first line. Nothing sits between the tap and the write. `grep -rn 'alertdialog\|window.confirm' src/ functions/` returns exactly one hit in the whole repo — `src/views/admin.js:46`, the self-demotion confirm — so this route has no confirmation primitive of its own.

**Equal, adjacent, thumb-side layout.** The two controls are siblings emitted by `node_modules/@basenative/admin/src/components.js:68-77` (`bn-admin-btn--ok` / `bn-admin-btn--no`, inside `<div class="bn-admin-queue__actions">`). `src/styles.css:443` lays them out as `.bn-admin-queue__actions { display: flex; gap: 10px; }`, and both get `flex: 1; min-height: 42px` (`src/styles.css:481-484` for `--ok`, `:485-488` for `--no`). At a 390px viewport that is two equal halves of the row, 10px apart, REJECT on the right.

**No recovery path.** `functions/_shared/d1.js:83-90` only does `UPDATE submissions SET status=?1, decided_by=?2, decided_at=unixepoch() WHERE id=?3` — the row survives, nothing is deleted. But `listPending()` (`functions/_shared/d1.js:77-81`) is `... FROM submissions WHERE status='pending' ORDER BY created_at`, and it is the only read of that table the product has. So the data is still there and there is no UI that can see it.

## The fix

Add the interstitial, and stop the two buttons reading as equals. The data-recovery half is deliberately a separate ticket (see Notes).

1. In `src/views/moderate.js`, add `const confirming = signal(null);` next to the existing `list` / `err` signals (line 16-17), holding the submission row awaiting confirmation.
2. Change the click delegation at `src/views/moderate.js:61-65`: when `btn.dataset.decision === "rejected"`, read the category and phrase out of the clicked `<li>` (`btn.closest(".bn-admin-queue__item")`, whose children are `.bn-admin-queue__cat` and `.bn-admin-queue__phrase` — see `@basenative/admin/src/components.js:62-68`) and `confirming.set({ id, category, phrase })` instead of calling `decide`. Leave the `"approved"` path committing immediately: approval is the reversible direction (the moderator can reject the resulting puzzle later), rejection is not.
3. Build the confirm modal with `renderDialog` from `@basenative/components` plus `fromHTML` from `../lib/dom.js`, copying the pattern already in `src/views/play.js:846-858`: `fromHTML(renderDialog({ id: "mod-reject", modal: true, closable: true, attrs: 'data-bn-region="reject-confirm"' }))`, then `setAttribute("aria-labelledby", …)` pointing at your own `<h2>` inside the body. Put the phrase itself in the body so the moderator confirms against the text, not an id.
4. Give it two buttons via `bnButton`: "Keep in queue" (`variant: "secondary"`) which just clears `confirming`, and "Reject this phrase" (`variant: "destructive"`) which calls the existing `decide(row.id, "rejected")` and then clears `confirming`. Focus the secondary one when the dialog opens. Unlike `play.js`'s end overlay, do **not** cancel the `cancel` event — Escape must dismiss this dialog, because dismissing is the safe outcome here.
5. Drive it with an effect mirroring `src/views/play.js:869-876`: `if (confirming() && !dlg.open && dlg.isConnected) dlg.showModal(); else if (!confirming() && dlg.open) dlg.close();` — the `isConnected` guard matters for the same reason it does there (the effect runs once at build time, before the tree is mounted, and `showModal()` on a detached `<dialog>` throws). Append the dialog to the `<main>` returned at `src/views/moderate.js:67-89`, alongside `errBox` and `queueRoot` (`:76-77`).
6. Stop the two controls reading as equal halves. In `src/styles.css:485-488` change `.bn-admin-btn--no` from `flex: 1` to `flex: 0 0 auto; min-width: 96px;` and raise `.bn-admin-queue__actions`'s `gap` (`src/styles.css:443`) from `10px` to `20px`. Restyle rather than reorder: the markup order is owned by `@basenative/admin`, so swapping the buttons would mean forking that package or DOM-shuffling after `innerHTML`, and the SSR first paint (`src/bn/views/moderate.js`, which calls the same renderer) would disagree with the hydrated tree.

Use `renderDialog`, not `window.confirm`: CLAUDE.md's "Things NOT to do" forbids reaching for a new dependency when a `@basenative/*` package covers it, `@basenative/components` is already installed and already used for a real `<dialog>` in `src/views/play.js`, and a native modal `<dialog>` gives focus containment, an inert background and focus restore for free — none of which `window.confirm` can be styled or labelled into.

## How we will know it worked

There is no DOM test harness in this repo — no jsdom in `devDependencies` (`package.json:49-56`), and `src/views/play.test.js` establishes the pattern for view files: read the source as text and assert on it (`src/views/play.test.js:15-33`). Follow it.

Add `src/views/moderate.test.js` with two source-scan assertions that both fail today:

1. `moderate.js` imports `renderDialog` — `assert.match(src, /renderDialog/)`.
2. The click delegation does not commit a rejection directly — assert that the `addEventListener("click"` handler body does not contain `decide(Number(btn.dataset.id), btn.dataset.decision)`. That exact expression is the defect; when it is replaced by a branch on `btn.dataset.decision`, the assertion passes.

Register the new file in `package.json`'s `"test"` script (it is an explicit `node --test <files…>` list, not a glob — an unregistered test file never runs).

By hand, on a 390px viewport: open `/moderate` as a moderator, tap REJECT, confirm a dialog appears with the phrase in it, press Escape, confirm the submission is still in the queue.

## Notes

- **Out of scope, and should be its own ticket:** a moderator-visible list of rejected submissions, and telling the submitter. The data is intact — `functions/_shared/d1.js:83-90` only UPDATEs the status — so a future `listDecided(status)` alongside `listPending()` (`functions/_shared/d1.js:77-81`) is all the store needs. This ticket deliberately stops at "you cannot mis-tap it" rather than "you can undo it"; do not expand it.
- `src/views/admin.js:46`'s `window.confirm` is the repo's only other destructive-confirm and is *not* the model to copy — replacing it with the same `renderDialog` pattern is a reasonable follow-up once this lands, but leave it alone here so the diff stays reviewable.
- The queue's inner markup belongs to `@basenative/admin` (`renderAdminQueueList`), and `src/views/moderate.js`'s file header says so explicitly. Anything structural has to be a CSS change here or a change upstream in BaseNative — not a local re-render of that HTML.
- `src/views/moderate.js:49-50` (`if (err()) { queueRoot.replaceChildren(); return; }`) is the error-handling shape T4-052 wants copied into `src/views/admin.js`. Same file, unrelated defect.
