## What the user hits

Someone follows a link with a typo in it — `t4bs.com/moderat`, `t4bs.com/play/123`, anything — and gets the lobby. Not a "that page doesn't exist, here's the lobby" message: the real, fully interactive lobby, with the wrong URL still in the address bar. There is no signal that the link was broken, so nobody reports the bad link and nobody learns their bookmark is wrong. The 404 page the codebase contains is only ever seen by crawlers and by visitors with JavaScript off.

## Why it happens

The server half is correct and the client throws it away.

Server: `matchRoute` (`src/bn/route-table.js:17-23`) returns `"not-found"` for anything not in the five-entry table, `functions/_shared/ssr.js:144` sets `status: route === "not-found" ? 404 : 200`, and `src/bn/views/not_found.js` renders `No page at <code>{{ pathname }}</code>` plus a link back to the lobby.

Client: `src/bn/client/hydrate.js:110` seeds the view signal from the SSR route —

```js
const view  = signal(routeToView(SSR.route));
```

— and `routeToView` (`src/bn/client/hydrate.js:709-718`) has no `not-found` case:

```js
case "lobby":
default:         return "lobby";
```

so `"not-found"` falls into the default and the app boots believing it is on the lobby. Nothing corrects it afterwards. The router effect (`src/bn/client/hydrate.js:160-167`) is a chain of `if`/`else if` over lobby/play/submit/moderate/admin with no final `else`, and `@basenative/router`'s `currentRoute()` returns `{ name: null, … }` for an unmatched path (`node_modules/@basenative/router/src/router.js:43`), so the chain simply does not fire and `view` keeps whatever it had. The view effect (`src/bn/client/hydrate.js:642-707`) likewise has arms for lobby/submit/moderate/admin/playing and nothing else.

Then `src/bn/client/hydrate.js:539-544` calls `mount(root, container, …)` where `root` is `document.getElementById("app")` (`src/bn/client/hydrate.js:463`) and `mount` is `host.replaceChildren(...)` (`src/lib/dom.js:99-101`). The SSR 404 `<main>` is discarded and the live lobby is mounted in its place.

The repo tests the server half only — `src/bn/hydrate.test.js:50-53` asserts `matchRoute("/wat") === "not-found"` and `:345-348` asserts the rendered template shows the pathname. There is no test for the client half, which is why this survived.

## The fix

Give the client a `not-found` view and a route arm that reaches it. Three edits plus a test.

1. Move `routeToView` out of `src/bn/client/hydrate.js:709-718` and into `src/bn/route-table.js` as an exported function, adding `case "not-found": return "not-found";` before the `default`. It belongs there — `route-table.js` is already the declared "single source of truth for the routes" (its file header) and is already pure, side-effect-free and imported by `src/bn/hydrate.test.js`, whereas `hydrate.js` runs an entire app at import time and cannot be loaded by `node --test`. Import it back into `hydrate.js`.
2. Add the missing branch to the router effect at `src/bn/client/hydrate.js:160-167`: a final `else view.set("not-found");`. `currentRoute().name` is `null` for an unmatched path, so this covers client-side navigation into a bad URL (`interceptLinks(document, router)` at `src/bn/client/hydrate.js:158` will intercept a same-origin link to one).
3. Add a `not-found` arm to the view effect (`src/bn/client/hydrate.js:642-707`). Reuse `mountNotice` (`src/bn/client/hydrate.js:594-608`) rather than writing a new view: it already mounts a `<main>` with an `sr-only` `<h1>`, a sticky-note title, a `bnAlert` and a "Go to the puzzle lobby" link — exactly the shape `src/bn/views/not_found.js` wants, and it is already the pattern for "you cannot see this route" gating. Call it with the pathname in the message, e.g. `mountNotice("Page not found", \`No page at ${window.location.pathname}.\`)`. Do **not** redirect to `/`: rewriting the URL is precisely the failure mode the route-access block at `src/bn/client/hydrate.js:546-556` documents as already fixed once for `/submit`, `/moderate` and `/admin`, and re-introducing it here would repeat that mistake.

## How we will know it worked

Add to `src/bn/hydrate.test.js`, next to the existing `matchRoute` describe block (`src/bn/hydrate.test.js:36-54`), a describe for `routeToView` asserting `routeToView("not-found") === "not-found"` alongside the five known routes. That test cannot be written at all today (the function is trapped inside `hydrate.js`), and it fails the moment step 1 is done without the new case — which is the point of doing step 1 first.

The mount-over behaviour is client-side and has no harness here (no jsdom in `devDependencies`, `package.json:49-56`). Check it by hand: `npm run build && npx wrangler pages dev dist --port 8788`, then visit `http://localhost:8788/wat`. Before: the lobby, with `/wat` in the address bar. After: the not-found notice, `/wat` still in the address bar, 404 still in the network tab. Also `curl -si http://localhost:8788/wat | head -1` must still show `404` — the server half must not regress.

## Notes

- `src/bn/client/hydrate.js` keeps its own inline copy of the route list when constructing the router (`:151-157`) rather than importing `routes` from `src/bn/route-table.js`. That duplication is a separate latent drift risk and is *not* part of this fix — but if you are already editing both files, collapsing it is cheap and in the spirit of that file's header. Mention it in the PR rather than silently widening the diff.
- `src/bn/views/not_found.js` stays as-is and stays reachable: it is what crawlers and no-JS clients get, and it is what carries the 404 status.
- Same root shape as T4-052 (a state the client can reach that no view renders honestly), but a different mechanism — that one is about error *copy* on views that do exist. No shared fix.
