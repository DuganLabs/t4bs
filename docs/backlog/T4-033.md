## What the user hits

Nobody using the game hits this. What it costs is on our side: there is no page-view data for t4bs at all, and on `main` every visitor's browser loads a beacon script that then fails a cross-origin request on every single page load. The site looks instrumented — a beacon tag in the HTML, analytics origins in the security policy — and records nothing.

## Why it happens

Two states, depending on which commit you are standing on.

**On `main` (`80aa7a8`, PR #100):** `src/bn/views/layout.js` carries a hand-written tag (verify with `git show main:src/bn/views/layout.js | sed -n '171,183p'`):

```html
<script
  defer
  src="https://static.cloudflareinsights.com/beacon.min.js"
  data-cf-beacon='{"token":"a6eb162865bb4319b158800e0b97b5cb"}'
></script>
```

The script loads fine — `ANALYTICS_SCRIPT_ORIGIN` is in `script-src` (`functions/_shared/security.js:164`, used at `:185`). But that token is the zone's **automatic-setup** token, and `cloudflareinsights.com/cdn-cgi/rum` answers an automatic-setup token used in a manual snippet *without* an `Access-Control-Allow-Origin` header, so the browser drops every report. Net: a failed cross-origin request per page load and zero RUM data — strictly worse than no beacon.

**On the branch `fix/analytics-honest` (`0a52711`, one commit ahead of `main`, not merged):** that tag is reverted — `src/bn/views/layout.js:169-171` now ends at the SSR-state block and `BN_HYDRATE_SCRIPT` with no beacon. That returns the site to the post-#99 state: Cloudflare's zone-level automatic injection emits an **inline** loader, which the CSP in `functions/_shared/security.js` refuses. It cannot be allowed — `script-src` (`functions/_shared/security.js:181-186`) carries only `'unsafe-hashes'`, the font-swap handler hash, the share-redirect hash and the `static.cloudflareinsights.com` origin, and no hash can cover text Cloudflare rotates with every beacon release. One console error per page load, still no analytics.

Either way both CSP origins are already in place and reached by nothing: `ANALYTICS_SCRIPT_ORIGIN` (`functions/_shared/security.js:164` → `script-src` at `:185`) and `ANALYTICS_REPORT_ORIGIN` (`:165` → `connect-src` at `:246`). The whole diagnosis, including why automatic setup cannot work under a CSP and exactly what dashboard action fixes it, is already written up in the comment block at `functions/_shared/security.js:60-80` — read it before touching anything.

## The fix

**This ticket cannot be finished from the code alone. Get the decision first** (see the `decision` field in the front matter) — the code-side work is one script tag either way, and it is inert without a token only the account holder can mint.

**If yes (we want analytics):**

1. Account holder, in the Cloudflare dashboard: Web Analytics → remove t4bs.com if present → add it with **Manual setup** → turn automatic injection **off** for the zone. Manual setup issues a token whose RUM endpoint answers with CORS headers; automatic setup's does not. Hand over the new token — it is public and ships in the HTML of every page, so it belongs in the repo.
2. Re-add the external script tag in `src/bn/views/layout.js`, immediately after the `<!--BN_HYDRATE_SCRIPT-->` line (`src/bn/views/layout.js:170` on the branch), with the new token. Use `git show 80aa7a8:src/bn/views/layout.js` as the template — the tag and its explanatory comment are already written; only the token changes. External `src`, never the inline loader: an external script needs only the host in `script-src`, which is already allowed.
3. Leave `functions/_shared/security.js` untouched — both origins are already there and correct.
4. Verify in a browser, not with curl. Cloudflare injects at the edge *after* the origin responds, so `curl` on the Pages origin cannot show you what ships; `functions/_shared/security.js:59-60` says exactly this ("Check the delivered document, not the origin response"). Open t4bs.com in DevTools: `beacon.min.js` 200, the POST to `cloudflareinsights.com/cdn-cgi/rum` 200 with an `Access-Control-Allow-Origin` header, no CSP violation in the console. Then confirm a page view appears in the dashboard.

**If no (we do not want analytics):**

1. Delete `ANALYTICS_SCRIPT_ORIGIN` and `ANALYTICS_REPORT_ORIGIN` (`functions/_shared/security.js:163-165`) and their uses in `script-src` (`:185`) and `connect-src` (`:246`). Removing the sole `connect-src` entry means the directive falls back to the baseline — confirm what `@basenative/middleware`'s baseline gives for `connect-src` before deleting the array, and keep `'self'` if the baseline does not already supply it (every fetch t4bs makes is same-origin `/api/*`, per the comment at `functions/_shared/security.js:236-245`).
2. Rewrite the comment block at `functions/_shared/security.js:60-80` to say the decision was made and analytics is deliberately absent — do not just delete it, or the next person re-derives the whole thing.
3. Account holder turns automatic injection off for the zone, otherwise the inline loader keeps getting refused and keeps logging a console error on every page load.

## How we will know it worked

`tests/security-headers.test.js` is the relevant test and it guards the CSP's shape, not the beacon's behaviour — whichever branch you take, run `npm test` and expect that file to stay green (or to be updated deliberately in the "no" case; it imports the origin constants, so deleting them is a compile-level failure there).

The defect itself is a live-service one and no test can catch it. The hand check is step 4 above, in a real browser on the real domain, looking for a 200 with CORS headers on the `/cdn-cgi/rum` POST. "The script loaded" is not evidence — that is exactly the state `main` is in now.

## Notes

- **Do not retry the automatic-setup token.** It has already been tried and reverted once (`80aa7a8` → `0a52711`). An automatic-setup token is not valid in a manual snippet, full stop.
- **Do not add `'unsafe-inline'` or a hash to admit Cloudflare's injected loader.** `'unsafe-inline'` throws away the CSP's main protection for one page-view counter, and the hash cannot work because Cloudflare rotates that text per beacon release.
- The branch `fix/analytics-honest` (`0a52711`) is the honest state and should be merged regardless of which way the decision goes — shipping a beacon that reports nothing is worse than shipping none. Merging it does not pre-empt the "yes" answer; step 2 above re-adds the tag with a working token.
- Cloudflare's edge injection is a known trap in this org (it injects after the origin responds, so a CSP must be verified in a browser). The `@basenative/middleware` limitation noted at `functions/_shared/security.js:212-214` — a baseline directive can be deleted but not narrowed — is a separate upstream issue and is not blocking here.
- The audit's original item #33 also covered a PendingBusiness-side analytics gap. That half is out of this repo's surface and is not tracked by this ticket.
