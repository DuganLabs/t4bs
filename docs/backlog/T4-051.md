## What the user hits

Someone shares their result in a chat app, the link gets truncated or mistyped on the way, and the recipient lands on a page that tells them "This share link has expired — the round it pointed to is gone." So they don't try again and don't ask the sender to resend, because the message says the thing is gone. Nothing in Tabs expires share links; the only way to see that page is an id that was never minted, which is exactly what a mangled link produces.

## Why it happens

The message is simply false. `functions/s/[id].js:75-80`:

```js
const card = await d1ShareCards(env.DB).get(id);
if (!card) {
  return new Response(notFoundPage("This share link has expired — the round it pointed to is gone."), {
    status: 404,
    …
```

There is no expiry anywhere in the share-card path:

- `migrations/0001_roles_and_share_cards.sql:13-22` defines `share_cards(id, session_id, user_id, category, score, won, grid, created_at)` — no expiry column. `migrations/0002_share_cards_puzzle_id.sql` only adds `puzzle_id`.
- `grep -rn 'DELETE FROM share_cards'` over the repo returns nothing.
- There is no scheduled/cron handler — `grep -n 'cron\|triggers\|scheduled' wrangler.toml functions/**/*.js` is empty.
- The reader applies no time filter: `functions/_shared/d1.js:163-168` is a plain `SELECT … FROM share_cards WHERE id=?1`. Contrast the readers that genuinely do expire — `d1Challenges.consume` (`functions/_shared/d1.js:207-215`) and `d1UserSessions.getUser` (`functions/_shared/d1.js:227-237`) both compare against `expires_at`.

So `!card` means "this id was never minted", not "this id aged out". The sibling message eight lines up already gets the register right — `functions/s/[id].js:69`, for an id that fails the `/^[a-z0-9]{4,16}$/i` shape check, says "This share link looks broken."

## The fix

1. `functions/s/[id].js:77` — replace the message with one that describes the only thing that can actually be true, and tells the recipient what to do: `"We couldn't find that share link — it may have been cut short on the way. Ask for it again, or play today's puzzle."` Keep the 404 and the `Cache-Control: no-store`.
2. Leave `functions/s/[id].js:69` (the malformed-id branch) as it is. Two distinguishable messages for two distinguishable causes is right; only the second one was lying. If you would rather have one message, collapse them into the malformed-id wording — but do not collapse them into the expiry wording.
3. Do not add an expiry to make the message true. Share cards are the growth mechanism; a link that stops working is a worse product than a table that grows. If retention ever becomes a real cost, that is its own ticket with its own copy.

## How we will know it worked

This is copy, and there is no test over `functions/s/[id].js`'s strings today. The cheap durable guard, if you want one, is a source-scan assertion in `tests/ssr-audit.test.js`'s style: read `functions/s/[id].js` and assert `/expired/i` does not appear in it. That fails before the change and passes after. Worth adding precisely because a false-mechanism string is the kind of thing that gets re-introduced by someone reasoning from the 404 status.

By hand: `npm run build && npx wrangler pages dev dist --port 8788`, then `curl -s http://localhost:8788/s/zzzzzz | grep -A1 '<h1>'`. Before: the expiry sentence. After: the new one. Confirm the status is still 404 (`curl -si … | head -1`) and that the "Play today's puzzle" link is still in the page (`functions/s/[id].js:60`).

Changing the *text* of a message does not touch that hash; changing the `<style>` block would, and `tests/security-headers.test.js` prints the new value if you do.
