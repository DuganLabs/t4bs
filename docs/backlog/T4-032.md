## What the user hits

On the submit form, someone types a brand-new category name — the hint literally invites it: "or type a new one" — and then taps straight into the Phrase field without tapping the `+ NEW CATEGORY "…"` row that appeared. The category field still shows what they typed, so the form looks complete. They fill in the phrase, pick their anchor letters, and SUBMIT FOR REVIEW stays greyed out. Nothing on the page says why.

## Why it happens

The combobox only commits its value on three exits, and "tapping somewhere else" is not one of them.

`src/views/submit.js:83-95` builds it with `allowCreate: true`, `onChange` and `onCreate` both writing into the `category` signal. Inside `@basenative/combobox` (v1.0.4 installed), a value reaches those callbacks only via `commit(entry)` (`node_modules/@basenative/combobox/src/combobox.js:325-350`), and `commit` is called from exactly three places:

- Enter while the popup is open — `combobox.js:392-400`
- Tab while a row is active — `combobox.js:411-419`
- a click on a row — `onListClick`, `combobox.js:423-434`

Every other dismissal goes through `onDocPointerdown` (`combobox.js:442-450`, registered capture-phase at `:477`), which does nothing but `setOpen(false)`. There is **no** blur or change handler on the input — the comment at `combobox.js:436-437` ("the input fires `blur` -> `setOpen(false)`") describes a handler that does not exist in this version. So the typed text stays in `input.value` while `category()` is still `""`.

SUBMIT is then disabled by `src/views/submit.js:188`:

```js
bindDisabled(submitBtn, () => busy() || !category() || !phrase() || anchorKeys().length === 0);
```

Four conditions, one boolean, and no message anywhere on the form that names which one failed. The hint at `src/views/submit.js:107-111` actively steers people down this path ("Tap to pick from N existing categories, or type a new one.").

**Correcting the original audit note:** the create row is *visible*, not screen-reader-only. `combobox.js:229-240` renders a real `<li role="option" data-bn-cb-create="true">` carrying `src/views/submit.js:92`'s `+ NEW CATEGORY "…"` label whenever the query is non-empty and unmatched. Only the "Press Enter to create" wording is announce-only (`combobox.js:272`). That visible row is why this is graded annoying rather than serious: a sighted user who re-focuses the field can recover.

## The fix

Two changes in `src/views/submit.js`. Fix it locally rather than waiting on `@basenative/combobox`: the blur semantics are genuinely arguable upstream (an implicit commit on blur is wrong for a strict picker), whereas t4bs *knows* it wants create-on-blur here, and the disabled-reason copy is t4bs's own product decision either way.

1. **Commit on blur.** In the `cbWrapper` `bind` callback (`src/views/submit.js:98-103`, which already has the hydrated element and calls `cb.hydrate(el)`), add a `blur` listener on the real input (`el.querySelector('input')`) that replays what `commit` would have done: read `input.value`, trim it, and if it is non-empty and does not already equal `category()`, case-insensitively match it against `existingCategories()` — on a match `category.set(match.toUpperCase())`, otherwise `category.set(value.toUpperCase())` (the create path, matching `onCreate` at `src/views/submit.js:94`). Guard against the click-on-a-row race by letting the package's own `onListMousedown` preventDefault do its job (`combobox.js:438-440` already stops the input from blurring on a listbox mousedown), and make the handler idempotent so a later `commit` for the same text is a no-op.
2. **Say which field is missing.** Replace the single opaque `bindDisabled` at `src/views/submit.js:188` with the same predicate *plus* a visible reason line: add a `<small data-bn-region="hint">` near the submit button whose `bindText` returns the first unmet condition — "Pick or add a category" / "Type the phrase" / "Tap at least one letter to reveal" / "" when everything is satisfied. Keep the button disabled (do not switch to enabled-and-validate-on-click); the disabled state is correct, it was just mute. Give the line `aria-live="polite"` so it is announced when it changes.

## How we will know it worked

No DOM harness exists in this repo (no jsdom in `devDependencies`, `package.json:49-56`), and both halves of this are DOM behaviour, so a unit test cannot cover the real defect. Two things to do instead:

1. A source-scan regression guard, in the style of `src/views/play.test.js:15-33`: a new `src/views/submit.test.js` asserting that `submit.js` registers a `blur` handler (`/addEventListener\(\s*["']blur/`) and that a submit-reason string exists. Register the file in `package.json`'s `"test"` list — it is an explicit `node --test <files…>` enumeration, not a glob, so an unregistered file never runs. This guards the fix from being reverted; it does not prove it works.
2. By hand, which is the real check: `npm run build && npx wrangler pages dev dist --port 8788`, sign in, go to `/submit`, type a category that does not exist, tap directly into the Phrase field without touching the dropdown, fill in a phrase and tap an anchor letter. Before: SUBMIT stays greyed with no explanation. After: SUBMIT enables, and the new category reaches the server (check the POST body, or `/moderate` afterwards).

## Notes

- **Why not fix it upstream:** `@basenative/combobox`'s handle exposes only `destroy/refresh/open/close/setOptions/_getVisible/_getQuery` (`combobox.js:501-520`) — there is no `commit` to call, which is why step 1 has to replay the logic rather than delegate. Adding an opt-in `commitOnBlur` option to the package is a reasonable follow-up (and CLAUDE.md's "don't introduce new direct dependencies if a `@basenative/*` package covers it" points that way long-term), but it must not block this ticket: the package is a published dependency (`^1.0.4`) and a version bump is a separate release cycle.
- The stale comment at `combobox.js:436-437` referring to a non-existent blur handler is worth reporting upstream when the above is filed — it is what makes this bug read as already-handled.
- Do not "fix" this by making the create row more prominent: it is already visible (`combobox.js:229-240`). The defect is the silent drop and the mute button, not discoverability.
