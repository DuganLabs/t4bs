## What the user hits

On `?legacy=1` — the documented escape hatch when SSR misbehaves — and on every local `npm run dev` session, primary buttons are invisible: no gold fill, and near-black label text (#1A0A00) on the near-black page (#0C0B09). The submit form appears to offer only "Cancel", because SUBMIT FOR REVIEW is rendered but unreadable. Anyone developing against `npm run dev` sees a broken app and anyone sent to `?legacy=1` to work around an SSR problem lands somewhere worse.

## Why it happens

A CSS cascade-layer priority inversion, in one line.

`index.html:54`, inside `<style data-bn-critical>`, has an **unlayered** rule:

```css
button{font:inherit;color:inherit;background:transparent;border:0}
```

The gold fill it overrides is **layered**: `node_modules/@basenative/components/src/components.css` opens with `@layer components {` on line 1, and the rule that paints the button is inside it at `components.css:138-141`:

```css
[data-bn="button"][data-variant="primary"] {
  background: var(--bn-color-primary-600);
  color: var(--bn-color-white);
}
```

Unlayered rules beat every layered rule regardless of specificity or source order. So `background: transparent` wins and the fill never paints.

The label colour then comes from `src/styles.css:334`, which is also unlayered (`grep -c '@layer' src/styles.css` finds only two, neither wrapping this) and higher specificity than the bare `button` selector:

```css
[data-bn="button"][data-variant="primary"]     { color: var(--bn-color-on-primary); }
```

`--bn-color-on-primary` is `#1A0A00` (`src/theme.css:79`) — a near-black chosen for contrast *against gold*, which is correct until the gold disappears. Secondary buttons survive only because `src/styles.css:317` sets their background unlayered too.

This is shell-specific, not build-specific. The SSR shell's critical block has the safe form — `src/bn/views/layout.js:78` is `button{font:inherit;color:inherit}` with no background or border reset — so production SSR renders gold. But `npm run dev` serves `index.html` (whose only entry is `<script type="module" src="/src/main.js">` at `index.html:117`), and production `?legacy=1` serves the built `dist/index.html` (`src/bn/route-table.js:29-31`: `if (search.get("legacy") === "1") return false;`), which carries the same block byte-for-byte. Both paths are broken live.

## The fix

1. Edit `index.html:54` to match the SSR shell: `button{font:inherit;color:inherit}`. Drop `background:transparent` and `border:0` outright — do not try to re-add them inside a layer or with `:where()`. The SSR block at `src/bn/views/layout.js:78` has shipped without them for the whole SSR era and no button in the app depends on a transparent default; the two shells' critical blocks are meant to mirror each other (`index.html:45-47` says exactly that) and one of them is simply wrong.
2. Check the handful of bare `<button>` elements that were relying on the reset. `[data-bn-action=logo]` is the one to look at — the SSR block covers it explicitly with `background:transparent;border:none` at `src/bn/views/layout.js:85`, so if `index.html`'s critical block does not carry an equivalent rule, add it there too rather than keeping the global reset. Everything else in the app renders through `bnButton`/`[data-bn="button"]` and is painted by the package.
3. Recompute the CSP hash. `LEGACY_CRITICAL_STYLE_HASH` (`functions/_shared/security.js:104-105`) is the sha256 of that exact block, so editing it invalidates the hash and first paint on `?legacy=1` silently goes unstyled in production. Run `npm test`; `tests/security-headers.test.js:313-323` recomputes it from the built `dist/index.html` and its failure message prints the value to paste in (`set it to: 'sha256-…'`). Paste it into `functions/_shared/security.js:105` and re-run.

## How we will know it worked

`tests/security-headers.test.js` is the test that moves. It runs `npm run build` itself (`tests/security-headers.test.js:317`) and then asserts the recomputed hash equals `LEGACY_CRITICAL_STYLE_HASH` (`:319-323`), so it **fails immediately after step 1** and passes again once step 3 pastes in the printed value. That failure is the signal the edit landed in the covered block; it is not an obstacle to work around.

The visual defect itself is a rendered-colour property no test in this repo can observe. Check by hand, both shells:

- `npm run dev`, open the lobby, confirm primary buttons render gold with dark legible text. (`/api` and `/og/*` do not work under Vite — that is expected and documented in CLAUDE.md — but the buttons are visible without them.)
- `npm run build && npx wrangler pages dev dist --port 8788`, then `http://localhost:8788/?legacy=1`, and confirm the same. Check the submit form specifically: SUBMIT FOR REVIEW should be gold beside a grey Cancel.
- With DevTools open on `?legacy=1`, confirm no CSP `style-src` violation in the console — that is what a stale hash looks like.

## Notes

- **The CSP hash trap.** Editing `index.html`'s `<style data-bn-critical>` block will fail `tests/security-headers.test.js` until the new hash is pasted into `functions/_shared/security.js:105`. That is by design (`tests/security-headers.test.js:13-19` explains why: "edit the critical CSS and first paint silently goes unstyled in production while every local check still passes"). The test prints the correct value.
- **Do not fix this by deleting `src/styles.css:334`.** That line is a deliberate interim shim for `@basenative/components` 0.7.0, which hardcodes `--bn-color-white` as the primary label colour — 2.46:1 on accent orange. The comment at `src/styles.css:319-333` says it becomes a no-op at 0.8.0 and is to be deleted with that version bump (fixed upstream in BaseNative#186). Removing it now reintroduces a contrast failure. The bug is the missing background, not the dark text.
- Vite does not minify inline `<style>` in HTML, so the source and built blocks are byte-identical and one hash covers both (`functions/_shared/security.js:99-103`).
- `src/styles.css:317`'s secondary-button background override is a separate standing correction (upstream's secondary paints `--bn-color-surface`, which in T4BS *is* the page background) — leave it.
- CLAUDE.md records `?legacy=1` as the fallback escape hatch and `src/main.js` as a BaseNative/signals entry, not the old React SPA. This ticket is what makes that escape hatch actually usable.
