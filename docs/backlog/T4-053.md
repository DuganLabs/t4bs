## What the user hits

Scrolling the lobby on a phone, the orange "+ SUBMIT A PHRASE" pill floats over the bottom-right of the viewport. Whatever category row happens to be passing under it mid-scroll has its right half swallowed: tapping there opens the submit form (or the sign-in modal) instead of opening the category. The row looks tappable across its whole width — it is a full-width 56px bar — and roughly half of it does something else.

## Why it happens

The end-of-page case has already been fixed; the mid-scroll case is a different thing and no amount of page padding can address it.

Already fixed: `src/styles.css:707-718` reserves clearance on the lobby `<main>` with `padding-bottom: 32px`, and its comment names this exact bug ("Clearance for the fixed '+ submit a phrase' FAB … at full scroll it covers the last 68px of the page. #app contributes 40px of that; this is the rest. Previously the element it landed on was the final free-play card, where a half-covered row still read as a row"). That is commit `e4999ee` / PR #98.

What remains: the control is viewport-fixed, so at any scroll position *other* than the bottom it sits over live content. `src/styles.css:767-775`:

```css
main[data-bn-view="lobby"] [data-bn-action="lobby-submit"] {
  position: fixed; right: 16px; bottom: calc(20px + env(safe-area-inset-bottom,0px)); z-index: 50;
  … font-family: 'Bebas Neue', sans-serif; font-size: 14px; letter-spacing: 1.5px;
  padding: 14px 22px; … min-height: 48px;
}
```

At Bebas 14px with 1.5px tracking and 22px side padding, "+ SUBMIT A PHRASE" is roughly 185px wide and 48px tall — about x∈[187,374] on a 390px viewport. The rows underneath it are the free-play shelf's `<summary data-bn="accordion-header">` elements (emitted by `renderBrowseShelf` → `renderAccordion`, `src/lib/game.js:195-205`; the `<summary>` is `node_modules/@basenative/components/src/accordion.js:33`), styled full-width at 56px tall with 14px/16px padding (`src/styles.css:917-922`), spanning about x∈[14,376]. Nothing lowers the pill's `z-index: 50` and nothing disables its pointer events, so the overlap is a live hit-target conflict: `src/views/lobby.js:199-204` wires the pill's `onClick` to `onSubmit`, which is either `router.navigate("/submit")` or `authOpen.set(true)` (`src/bn/client/hydrate.js:646-649`).

PR #98 made this *more* likely, not less: turning the shelf into an expandable accordion is what made the lobby reliably long enough to scroll.

## The fix

Stop the control from floating over content. Pick the anchored option, not the hide-on-scroll option.

1. In `src/styles.css:767-775`, drop `position: fixed` and the `bottom`/`right`/`z-index` triple. Move the pill into the normal flow at the end of the lobby column — it is already the second-to-last child of `<main>` in `src/views/lobby.js` (the rules note follows it), so give the lobby `<main>` `align-items: center` (already set, `src/styles.css:709`) do its work and let the pill sit as its own row with `margin: 4px 0` and `align-self: flex-end` if you want to keep the right-hand placement.
2. Remove the now-unneeded `padding-bottom: 32px` from `src/styles.css:717` **and** rewrite the comment above it (`src/styles.css:711-717`) so the next reader is not told about clearance for a fixed element that is no longer fixed. Leaving a stale comment there is how this bug gets re-introduced.
3. Leave `src/views/lobby.js:199-204` alone — the element, its `aria-label` and its handler are all correct; only its positioning is wrong.

Anchor it rather than keeping it fixed and hiding it on scroll, or shrinking it, or lowering its `z-index`: a hide-on-scroll FAB needs a scroll listener and a threshold and still overlaps during the transition; a smaller pill overlaps a smaller strip of every row; and lowering `z-index` below the rows makes the control unclickable rather than making the rows clickable. Anchoring removes the class of bug instead of narrowing it. Submitting a phrase is not the lobby's primary action — picking a category is — so it does not need to be permanently on screen.

## How we will know it worked

This is layout and there is no visual-regression or DOM harness in the repo (no jsdom in `devDependencies`, `package.json:49-56`; `tests/*.test.js` are source scans and rendered-HTML string checks). A CSS assertion is the only automatable guard: add to `tests/components-adoption.test.js` — which already walks every `src/**/*.{js,css}` file (`tests/components-adoption.test.js:22-30`) — an assertion that the `[data-bn-action="lobby-submit"]` rule in `src/styles.css` does not contain `position: fixed`. That fails today and passes after.

The real check is by hand, and must be done at a phone width: `npm run build && npx wrangler pages dev dist --port 8788`, open the lobby in DevTools device mode at 390×844 with enough approved puzzles that the page scrolls, and scroll slowly. Before: the pill sits over the right half of whichever `<summary>` row is passing it, and tapping there opens `/submit`. After: no overlap at any scroll position, and every row is tappable across its full width. Also confirm the pill is still reachable and still focusable in tab order.

## Notes

- Status is `partially-fixed`, not `open`: `e4999ee` / PR #98 genuinely closed the end-of-page half. Do not re-apply that clearance — read `src/styles.css:711-717` first so you know what is already there and why.
- PR #98's accordion change (`renderBrowseShelf`, `src/lib/game.js:195-205`) is what made the lobby scrollable; the FAB and the accordion are not independently at fault, the combination is.
- The `padding-bottom` also currently protects the rules note at the very end of `<main>`. If step 1 is done but step 2's padding removal is skipped, nothing breaks — it just leaves 32px of dead space. Removing it is tidiness, not correctness.
- `#app` contributes 40px of bottom padding of its own (`src/bn/views/layout.js:75`, mirrored in `index.html:52`), which is where the "68px total" arithmetic in the existing comment comes from.
