## What the user hits

A player taps ALL IN — the one-shot bet that pays a bonus if the whole phrase is right and costs every remaining life if it is not — and the red bar under the header tells them to press SHOVE to commit. There is no SHOVE anywhere: not a button, not a key, not a label. Directly above that bar, the normal-play hint is still there telling them to "TYPE 4 MORE LETTERS FOR WORD 1", so the screen gives two contradictory instructions at once, on the single most expensive action in the game.

## Why it happens

Two independent bugs on the same screen.

**The phantom control.** `src/views/play.js:84`:

```js
if (allInMode()) return `ALL IN — type the rest of the phrase · SHOVE to commit · +${allInBonus()} pts if right · 0 lives if wrong`;
```

`grep -rn SHOVE src/ functions/ shared/ index.html` returns that one line and nothing else. Committing is `enter()` (`src/views/play.js:187-192`, which routes to `submitAllIn()` when `allInMode()`), reached either by the hardware Enter key (`src/views/play.js:380`: `if (e.key === "Enter") { e.preventDefault(); enter(); }`) or by the on-screen keyboard's primary action (`src/views/play.js:679-690`, `primary: "ENTER"` with `onAction: (a) => { if (a === "ENTER") enter(); … }`). The button that opened the mode has meanwhile relabelled itself to FOLD (`src/views/play.js:698`: `bindText(allInBtn, () => allInMode() ? "FOLD" : "ALL IN")`), so it is not the commit control either. The same wrong word is in the screen-reader announcement at `src/views/play.js:317`: `announcement.set("All-in mode. Type the rest of the phrase to shove.")`.

**The contradictory hint.** `openAllIn()` clears the per-word focus with `active.set(null)` (`src/views/play.js:316`) and clears the typed letters with `typed.set(s.words.map(() => []))` (`src/views/play.js:314`). But the focus effect at `src/views/play.js:109-117` reads `active()` and has no `allInMode()` guard:

```js
effect(() => {
  if (phase() !== "playing" || casc()) return;
  const ws = wordSolved();
  const a = active();
  if (a === null || ws[a]) {
    const next = ws.findIndex(s => !s);
    if (next !== -1) active.set(next);
  }
});
```

so it immediately re-sets `active` to the first unsolved word. `hintText` (`src/views/play.js:66-79`) then falls through to `return \`Type ${room} more letter${…} for word ${active() + 1}.\`` — and because `typed` was just cleared, `room` is the whole word. `hintEl` sits directly above `cbarEl` in the summary header (`src/views/play.js:443-449`), and both are visible: `cbarEl` is only hidden when neither cascade nor all-in is active (`src/views/play.js:441`), and `hintEl` has no hidden binding at all (styled at `src/styles.css:1006-1011`, `min-height: 14px`).

## The fix

1. `src/views/play.js:84` — replace `SHOVE to commit` with `ENTER to commit`. ENTER is the correct name for both paths: it is the literal label of the on-screen primary key (`src/views/play.js:681`, `primary: "ENTER"`) and the hardware key handled at `src/views/play.js:380`. Do not invent a SHOVE button instead — the poker metaphor is already carried by ALL IN / FOLD / the stake language, and adding a second commit control means a second code path into `submitAllIn()` plus a keyboard-layout change in `@basenative/keyboard`.
2. `src/views/play.js:317` — change the announcement to match: `"All-in mode. Type the rest of the phrase, then press Enter to commit."` Screen-reader copy and visible copy must name the same key.
3. `src/views/play.js:109-117` — add `if (allInMode()) return;` as the second line of that effect, immediately after the `phase()`/`casc()` guard. This is safe and is the right place: nothing in ALL IN reads `active`. `typeLetter` branches on `allInMode()` first and uses `findGlobalNextSlot()` (`src/views/play.js:147-152`), the keydown effect's guard already admits `allInMode()` with a null `active` (`src/views/play.js:375`: `(active() === null && !allInMode())`), and the grid explicitly suppresses the active-word highlight in the mode (`src/views/play.js:482`: `const isAct = !allInMode() && active() === wi && …`). On FOLD the effect re-runs — it now reads `allInMode()` — and restores focus to the first unsolved word, which is what `openAllIn`'s fold branch (`src/views/play.js:306-310`) wants.
4. Belt and braces, because the hint is the thing the player actually reads: add `if (allInMode()) return "";` to `hintText` at `src/views/play.js:66-79`, right after the `casc()` check. Step 3 alone fixes today's bug; this makes a future write to `active` unable to reintroduce it.

## How we will know it worked

There is no DOM test harness — no jsdom in `devDependencies` (`package.json:49-56`). `src/views/play.test.js` is the established pattern for this file: it reads `play.js` as source text (`src/views/play.test.js:26`, with a `stripComments` helper at `:23-24`) and asserts on it.

Add to `src/views/play.test.js`, in the same source-scan style, two assertions that fail today:

1. `assert.equal(/SHOVE/.test(playSource), false, "ALL IN mode must name a control that exists — the commit key is ENTER")`. Note that `stripComments` is already applied, so a mention of the word in a comment will not trip it.
2. `assert.match(playSource, /if \(allInMode\(\)\) return;/)` scoped to the focus effect — simplest reliable form is to slice the source from `const ws = wordSolved()` backwards to the preceding `effect(` and assert the guard is inside that slice.

The mid-mode hint contradiction itself is a rendered-DOM property no test here can observe. Check it by hand: `npm run build && npx wrangler pages dev dist --port 8788`, start any round, type nothing, tap ALL IN, and confirm the hint line above the red bar is empty and the red bar reads "ENTER to commit". Then tap FOLD and confirm the per-word hint comes back.
